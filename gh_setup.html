GitHub for Educators: Interactive Walkthrough

Practise the whole account-to-published-site path in a simulation first, following Professor Alex Rivera through eight steps — nothing you do here touches a real account.

⏱ 20 min 📑 8 steps 🎯 Walkthrough

Why this matters

Most faculty stall on GitHub at the same three screens: the sign-up form, the new-repository dialogue, and the Pages settings panel. Clicking through them once in a simulation, where a wrong choice costs nothing, removes the hesitation that otherwise ends the attempt.

This page has a companion — use both

Module 5 teaches the account → repository → publish procedure twice, on purpose, in two different formats. They are not duplicates and neither replaces the other:

  • This page is the practice simulation. Eight clickable steps with a mocked-up GitHub interface. Nothing is real, so nothing can break. Use it first, to see the shape of the whole path before you commit to anything.
  • Publishing with GitHub Pages is the written reference. Ten steps in full detail, a troubleshooting section, and the part this page does not cover at all — the GitHub Educator Benefits application, which is how you get Pro, Copilot and Codespaces free with a .edu address. Keep it open beside the real site while you do the work for real.

Order that works: run the simulation here, then follow the written reference on the live site.

Learning objectives

By the end of this walkthrough you will be able to:

  1. Create a GitHub account with a username and institutional email that work for you long term.
  2. Configure a faculty profile that a student or colleague can read as a credential.
  3. Create a repository for a course, choosing its name, visibility, and README setting deliberately.
  4. Publish that repository as a live website at your own address using GitHub Pages.

Prerequisites and what you will need

For the simulation on this page: nothing. It runs entirely in your browser and creates no account.

For doing it for real afterwards:

  • Your institutional .edu email address, and access to that inbox — GitHub sends a six-digit code that expires in fifteen minutes.
  • A username you are willing to keep. It becomes part of every address you ever share, so decide before you type.
  • Any files you want to publish. They can wait; the account and repository come first.
  • About twenty minutes. Approval of educator benefits takes days, but publishing does not depend on it.

Before step 1

What You Will Have at the End

The whole eight-step path exists to produce one thing. Knowing what it is makes the intermediate screens make sense.

The finished artifact

A live web address that anyone can open, with no GitHub account and no login. In the simulation, Alex Rivera finishes holding this:

https://alexrivera-edu.github.io/comm101-resources

Behind that address sits a repository containing a README, a syllabus PDF, and a week-01 folder. Editing any file in the browser republishes the site within a minute or two, so the address in your syllabus never goes stale. That is the whole point: one link that always shows the current version.

Practise

Interactive Walkthrough

Select any step pill to jump to that step, or use Next and Previous to work through in order. Each step shows one decision and a simulated version of the screen you will meet.

Verification — you are done when

Once you have repeated the eight steps on the real site, you are finished when all five of these are true. Anything less and the link in your syllabus will fail for somebody.

  • You can open https://your-username.github.io/your-repo and see your own content, not a 404 page. (Step 8)
  • It still loads in a private or incognito window, signed out. That is the actual test — a signed-in tab will show you a repository a student cannot reach. (Step 5, Public vs. Private)
  • Your repository shows a green tick beside the most recent commit in the Pages settings panel. (Step 8)
  • You edited one file in the browser, committed it, waited two minutes, and saw the change appear at the live address. (Step 7)
  • Your profile shows your real name and institution, so the address reads as a faculty resource rather than an anonymous one. (Step 4)

When it goes wrong

Troubleshooting Common Errors

These are the five places faculty actually get stuck when they leave the simulation and do it for real.

The verification code never arrives (Step 2)

Institutional mail filters block GitHub more often than personal ones. Check junk and quarantine first, wait a full three minutes before requesting a new code, and remember the code expires after fifteen minutes — an old one in your inbox will simply be rejected.

Your live address returns 404 (Step 8)

Four causes, in order of likelihood: the repository is Private, not Public; there is no file named exactly index.html at the root; Pages was never actually saved in Settings; or the first build has not finished. Give it ten minutes before assuming it is broken.

Your edit does not show up on the site (Step 7)

Editing a file in the browser is not enough — you have to scroll down and commit the change. If you did commit, the site rebuilds in one to two minutes; force-refresh the page, because your browser is probably showing you a cached copy.

You picked a username you now regret (Step 1)

You can rename an account, but every existing address breaks and GitHub does not forward the old one. Since the username is baked into every link you will hand to students, this is the one decision worth pausing on before you press Continue.

Educator benefits never activate (Step 3)

The onboarding wizard does not grant them. They are a separate application on the GitHub Education site, they require your .edu address to be verified on the account, and approval takes days. This page does not cover that application — the written reference does.

Quick check

You finish the simulation, create a real repository, upload your files, and turn on Pages. A colleague emails to say your link shows “404 — There isn't a GitHub Pages site here.” It loads perfectly for you. What is the most likely cause?

Right — and note why your own browser hid the problem: you are signed in, so you can see your own private repository and its site. This is exactly why the verification step tells you to test in a private window. Switch the repository to Public in Settings and the link works immediately.
Not quite. Pages builds in one to two minutes, not a day, and no account is needed to view a published site. The giveaway is “it loads for you” — you are signed in, so a Private repository still renders for you and for nobody else. Set it to Public.

Try this in your classroom

Publish one artefact your students already ask for repeatedly — the syllabus, the assignment schedule, the lab safety sheet — and replace the LMS attachment with the live link. Then update it mid-semester and watch that nobody has to be told the old copy is out of date. Step 2 of this walkthrough is also a natural five-minute discussion of why platforms send one-time codes instead of links.

Key takeaways

  • The username is the one irreversible choice in sign-up: it becomes part of every address you hand out, and renaming later breaks all of them.
  • A profile with a real name, a one-line bio and an institution turns a bare address into something a student reads as a faculty resource.
  • A repository is a course folder that keeps every version. Public plus a README is the combination that makes it usable by students; Private silently hides it from them.
  • GitHub Pages turns that repository into a free website at a permanent address that needs no login to view and republishes itself every time you commit.
